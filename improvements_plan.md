# План доработок системы Overtime

## 1. Оптимизация размера Docker-образа бэкенда (CPU-only PyTorch)
* **Статус:** ✅ **Выполнено**
* **Цель:** Сократить размер Docker-образа бэкенда с ~10 ГБ до ~2 ГБ, а также уменьшить потребление диска и ОЗУ на сервере.
* **Описание:** Поскольку проект развернут на CPU-сервере без дискретных видеокарт Nvidia CUDA, библиотека PyTorch с CUDA-драйверами (532 МБ скачиваемого архива и гигабайты распакованных библиотек CUDA) избыточна.
* **Реализация:**
  * В [Dockerfile.base](file:///home/nik/Dev/overtime-prod/backend/Dockerfile.base) настроена установка CPU-версий `torch` и `torchaudio` напрямую из официального репозитория PyTorch (`https://download.pytorch.org/whl/cpu`).
  * Для предотвращения лишней нагрузки удаляется библиотека `triton` (нужная только для GPU-вычислений).

## 2. Предварительная загрузка ML-моделей в Docker-образ
* **Статус:** ✅ **Выполнено**
* **Цель:** Исключить долгое скачивание моделей (Whisper и Gazeta) из интернета при первом запуске контейнера или первом голосовом запросе пользователя.
* **Описание:** Модели Whisper и RuT5 скачиваются и кэшируются в Docker Volume при первом запуске контейнера. Ранее использовалась gazeta. В настоящее время используется rut5-base для суммаризации текстов.
* **Реализация:**
  * Создан скрипт [download_models.py](file:///home/nik/Dev/overtime-prod/backend/scripts/download_models.py), скачивающий Whisper "base" и T5 "rut5_base_sum_gazeta" в папки `/app/.cache/whisper` и `/app/models/`.
  * В [entrypoint.sh](file:///home/nik/Dev/overtime-prod/backend/scripts/entrypoint.sh) настроен асинхронный фоновый запуск скрипта скачивания при первом старте контейнера, что позволяет веб-серверу Uvicorn запускаться мгновенно без ожидания загрузки моделей. После завершения скачивания создается маркер-файл `/app/models/.models_ready`.

## 4. Смарт-фильтры статусов согласования (Пункт 1)
* **Статус:** ✅ **Выполнено**
* **Цель:** Исключить потерю заявок на промежуточных этапах согласования (`MANAGER_APPROVED`, `HEAD_APPROVED`) и предоставить руководителям персонализированный список входящих задач.
* **Реализация:**
  * По умолчанию при входе на `/review` активируется смарт-пресет **«Требует моего решения»** (`action_required`).
  * Для менеджера отображаются заявки, где `manager_approved IS NULL` (статусы `PENDING`, `HEAD_APPROVED`).
  * Для начальника отдела — заявки по его отделу, где `head_approved IS NULL` (статусы `PENDING`, `MANAGER_APPROVED`) с учетом dual-role.
  * Добавлен пресет **«Все на согласовании»** (`in_review`), объединяющий все незавершенные заявки, и пресет **«Все заявки»** (`all`).
  * Реализовано в `backend/app/repositories/overtime.py`, `backend/app/api/v1/overtime.py` и `frontend/src/components/pages/ReviewPage.tsx`.

## 5. Синхронизация Календарного вида с фильтрами (Пункт 2)
* **Статус:** ✅ **Выполнено**
* **Цель:** Устранить рассинхрон между ячейками календаря и правой панелью детального списка заявок.
* **Реализация:**
  * Эндпоинт `GET /api/v1/overtimes/calendar-summary` принимает параметры `preset`, `status` и `department_id`.
  * Ячейки дней календаря рассчитывают часы и список сотрудников **строго по заявкам, соответствующим выбранному фильтру**.
  * Дни без заявок по выбранному фильтру остаются прозрачными/пустыми, что обеспечивает 100% совпадение с колонкой деталей («Найдено: 0»).
  * Реализовано в `backend/app/repositories/overtime.py`, `backend/app/api/v1/overtime.py` и `frontend/src/components/pages/review/ReviewCalendarView.tsx`.

## 6. Двухрежимное отображение круговой диаграммы аналитики (Пункт 3)
* **Статус:** ✅ **Выполнено**
* **Цель:** Устранить ошибку с отображением штук заявок как часов (`138.0ч`) и дать возможность анализировать структуру как в штуках, так и в часах.
* **Реализация:**
  * В бэкенд добавлены поля распределения часов по статусам: `approved_hours`, `pending_hours`, `rejected_hours`.
  * Над диаграммой «Статусы заявок» внедрен переключатель режимов:
    1. **«По количеству заявок (шт.)»**: отображение `{name}: {count} шт. ({percent}%)`.
    2. **«По объему часов (ч.)»**: отображение `{name}: {hours} ч. ({percent}%)`.
  * Реализовано в `backend/app/schemas/analytics.py`, `backend/app/repositories/analytics.py` и `frontend/src/components/pages/AnalyticsPage.tsx`.

## 7. Кэширование токена авторизации MS Graph (Пункт 7)
* **Статус:** ✅ **Выполнено**
* **Цель:** Устранить задержку в 300–700 мс при отправке каждого письма (OTP, нотификации) и исключить избыточные запросы к Azure AD.
* **Реализация:**
  * `ConfidentialClientApplication` инициализируется как Singleton один раз в `__init__` сервиса `MSGraphService`.
  * Использование встроенного механизма `acquire_token_silent(scope, account=None)`. Запрос нового токена выполняется только при истечении срока валидности текущего.
  * Реализовано в `backend/app/services/ms_graph.py`.

## 8. Реактивное обновление согласований через WebSocket (Пункт 8)
* **Статус:** ✅ **Выполнено**
* **Цель:** Обеспечить мгновенную актуализацию данных на экранах согласующих лиц без ручной перезагрузки (F5).
* **Реализация:**
  * Сервер рассылает событие `OVERTIME_STATUS_CHANGED` при создании, согласовании, отклонении, отмене, восстановлении и обновлении заявок.
  * Клиент тихо обновляет список заявок и данные календаря без сброса выделенных чекбоксов.
  * Создан глобальный компонент `ToastNotification`, отображающий информативные кликабельные уведомления в углу экрана.
  * Реализовано в `backend/app/services/overtime.py`, `frontend/src/components/layout/NotificationBell.tsx`, `frontend/src/components/atoms/ToastNotification.tsx` и `frontend/src/App.tsx`.
* **Принятые решения:**
  * Бэкенд через `WebSocketManager` рассылает событие `OVERTIME_STATUS_CHANGED` ролям `admin`, `head`, `manager` при любых действиях согласования.
  * Фронтенд на `/review` слушает сокет и выполняет **бесшовный фоновый рефреш** данных без показа блокирующего лоадера и без сброса активных чекбоксов выбора.
  * В правом нижнем углу всплывает аккуратное интерактивное **Toast-уведомление** («Заявка #... согласована [ФИО]») с возможностью клика для перехода.
