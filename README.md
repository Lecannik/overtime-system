# 🕒 OvertimePro (Система учета переработок)

**OvertimePro** — это современная корпоративная система для автоматизации учета, согласования и аналитики внеурочных работ (переработок). Система позволяет эффективно управлять ресурсами компании, прозрачно отслеживать затраты времени и формировать отчетность для принятия управленческих решений.

---

## ✨ Основные возможности

*   **👥 Ролевая модель доступа**: 
    *   **Сотрудник**: Создание заявок на переработку, просмотр личной статистики.
    *   **Менеджер**: Согласование заявок своей команды, аналитика по курируемым проектам.
    *   **Начальник отдела**: Контроль бюджета времени всего отдела, утверждение заявок после менеджеров.
    *   **Администратор**: Полный доступ к управлению пользователями, отделами, проектами и глобальной аналитике.
*   **🏢 Администрирование и структуры**:
    *   **Отделы и Проекты**: Переключение представлений (**Табличный вид** / **Карточный вид**) с сохранением предпочтений пользователя в `localStorage`.
    *   **Умная фильтрация и поиск**: Мгновенный поиск по названиям, кодам проектов, руководителям и ID; сортировка по любым колонкам в таблице, фильтры по активности и менеджерам.
    *   **Быстрое редактирование**: Изменение статусов проектов в один клик, автосохранение лимитов часов и инлайн-редактирование.
*   **📜 Журнал аудита и безопасности**:
    *   **Детализированная история**: Полное логирование всех системных и пользовательских событий (авторизация, смена паролей, согласования, корректировки времени, отмена заявок) с человекочитаемыми описаниями на русском языке.
    *   **Глубокий поиск**: Фильтрация логов по ФИО, Email, типу действия, ID и содержимому параметров.
    *   **Выгрузка отчетов в Excel**: Экспорт отфильтрованного журнала аудита за выбранный период (день, неделя, месяц, квартал или произвольный диапазон) в брендированный `.xlsx` файл.
*   **📋 Умное согласование и смарт-фильтры**:
    *   **Пресеты согласования**: Быстрое переключение между фильтрами «Требует моего решения» (активен по умолчанию), «Все на согласовании» и «Все заявки».
    *   **Синхронизация календаря**: Интерактивный heatmap-календарь полностью синхронизирован со смарт-пресетами, статусами и отделами.
    *   **Реактивные WebSocket-обновления**: Мгновенное обновление списков и календаря без потери выбранных чекбоксов, а также всплывающие кликабельные Toast-уведомления об изменении статусов заявок.
*   **📊 Аналитическая панель**:
    *   Визуализация трудозатрат в разрезе проектов, отделов и конкретных сотрудников за любые периоды.
    *   **Двухрежимная диаграмма статусов**: Переключение круговой диаграммы между «По количеству заявок (шт.)» и «По объему часов (ч.)» с корректным выводом процентов и единиц измерения.
*   **📂 Экспорт отчетов**: Выгрузка детальных данных в Excel с автоматическим расчетом итогов и профессиональным форматированием.
*   **🔐 Безопасность и интеграции**: 
    *   Двухфакторная аутентификация (OTP) через Microsoft Office Integration и контроль прав на уровне API (Security at Depth).
    *   **In-Memory кэширование MS Graph**: Оптимизация авторизации в Azure AD через MSAL Singleton (`acquire_token_silent`).
*   **⚖️ Умный расчет**: Автоматический подсчет часов с учетом правил округления на стороне базы данных.
*   **🔌 Интеграция с Odoo CRM**: Двухрежимный импорт проектов:
    *   **XML-RPC**: Импорт всех проектов напрямую.
    *   **FastAPI Connector**: Выборочная выгрузка с динамическим выбором полей, частичной серверной и клиентской фильтрацией по названию/номеру проекта, а также пакетным добавлением.

## 🚀 Быстрый старт

### Способ 1: Использование Docker (Рекомендуется)

1.  Клонируйте репозиторий:
    ```bash
    git clone https://github.com/your-repo/overtime-system.git
    cd overtime-system
    ```
2.  Создайте файл `.env` на основе примера:
    ```bash
    cp .env.example .env
    ```
3.  Запустите проект:
    ```bash
    docker-compose up --build
    ```
    Миграции базы данных применятся автоматически при запуске бэкенд-контейнера. Система будет доступна по адресу `http://localhost:8090` (через Nginx Gateway).

### 🔑 Создание администратора по умолчанию

Для создания первоначальной учетной записи администратора выполните команду:
```bash
docker-compose exec backend python scripts/create_admin.py
```
или при локальном запуске:
```bash
python scripts/create_admin.py
```
Скрипт автоматически создаст пользователя с email `admin@example.com`, сгенерирует безопасный случайный временный пароль и установит флаг смены пароля при первом входе.

### Способ 2: Локальный запуск (для разработки)

#### Backend
1. Перейдите в папку `backend`:
   ```bash
   cd backend
   python -m venv venv
   source venv/bin/activate  # Или venv\Scripts\activate для Windows
   pip install -r requirements.txt
   ```
2. Запустите сервер:
   ```bash
   uvicorn app.main:app --reload
   ```

#### Frontend
1. Перейдите в папку `frontend`:
   ```bash
   cd frontend
   npm install
   ```
2. Запустите dev-сервер:
   ```bash
   npm run dev
   ```

## ⚙️ Настройка окружения (`.env`)

Для корректной работы системы необходимо настроить следующие переменные в файле `.env`:

*   `POSTGRES_...` — параметры подключения к базе данных.
*   `SECRET_KEY` — секретный ключ для создания JWT-токенов.
*   `ENABLE_DOCS` — флаг включения интерактивной документации Swagger UI / ReDoc (`/docs`, `/redoc`, `/openapi.json`). В целях безопасности на продакшне строго `False`.
*   `MS_...` — параметры интеграции с почтовым сервисом Microsoft для отправки уведомлений и кодов OTP.
*   `ODOO_INTEGRATION_URL` — URL-адрес микросервиса интеграции с Odoo CRM (например, `http://localhost:8000`).
*   `ODOO_INTEGRATION_KEY` — X-API-Key токен авторизации для безопасного взаимодействия с микросервисом Odoo CRM.

Полный список доступен в файле [`.env.example`](./.env.example).

## 🌐 Развертывание (Production Deployment)

Продакшн-версия системы развертывается по принципу инфраструктуры без исходного кода на целевом сервере (Source-code-free Deployment):

1. **Сборка и доставка**:
   * Сборка Docker-образов бэкенда (`lecannik/overtime-backend`) и фронтенда (`lecannik/overtime-frontend`) выполняется автоматически в CI-пайплайне GitHub Actions.
   * Образы тегируются уникальным SHA коммита (`IMAGE_TAG=${{ github.sha }}`) и отправляются в реестр DockerHub.
2. **Деплой на сервере**:
   * GitHub Actions Runner (`git-runner`) с помощью протокола `scp` копирует на сервер деплоя файлы конфигурации: `docker-compose.prod.yml` и `nginx.conf`.
   * По протоколу `ssh` на сервере выполняется обновление контейнеров:
     ```bash
     export IMAGE_TAG=<commit_sha>
     docker compose -f docker-compose.prod.yml pull
     docker compose -f docker-compose.prod.yml up -d
     ```
3. **Запуск административных скриптов на продакшене**:
   Так как исходный код встроен в Docker-образы, служебные скрипты запускаются непосредственно внутри контейнеров хост-командами:
   * Создание учетной записи администратора:
     ```bash
     docker compose -f docker-compose.prod.yml exec backend python scripts/create_admin.py
     ```
   * Накатывание миграций базы данных (выполняется автоматически при старте бэкенда или вручную):
     ```bash
     docker compose -f docker-compose.prod.yml exec backend alembic upgrade head
     ```

## 🔐 Архитектура аутентификации и безопасности

В системе реализован гибридный, отказоустойчивый механизм аутентификации. Подробное техническое задание и спецификация API описаны в документе [docs/auth_specification.md](file:///home/nik/Dev/overtime-prod/docs/auth_specification.md).

1. **Гибридный вход (Hybrid Auth)**:
   * **Локальная аутентификация**: По логину и хешированному паролю (`bcrypt`) с поддержкой **2FA OTP** через Microsoft Graph API.
   * **Корпоративный SSO**: Авторизация по протоколу OIDC через **Authentik / Microsoft Entra ID** с автоматическим созданием учётной записи (Provisioning) при первом входе.
2. **Безопасная работа с токенами (In-Memory Access Token + HTTPOnly Refresh Cookie)**:
   * **Access Token (JWT)** хранится исключительно в памяти браузера (`inMemoryToken`), исключая утечку токенов через XSS/localStorage.
   * **Refresh Token** хранится в защищенной куке (`HttpOnly`, `SameSite=Lax`, `Secure`).
   * **Token Rotation & Grace Period**: Серверный механизм в `refresh_token.py` аннулирует старый Refresh Token при каждом обновлении, обеспечивая 10-секундный grace period для синхронизации параллельных запросов клиента (`asyncio.Event`).
3. **Защита SSO (CSRF & Privacy)**:
   * **OIDC State CSRF Protection**: Переход на страницу авторизации SSO сопровождается генерацией криптографического `state`-токена и его проверкой на этапе callback через куку `oauth_state`.
   * **Безопасный редирект**: После успешного входа через SSO Access Token **не передается в URL query**. Вместо этого клиент выполняет прозрачный фоновый `refreshAccessToken()` с использованием установленной куки сессии.
4. **Защита документации API (Swagger/OpenAPI)**:
   * Эндпоинты `/docs`, `/redoc` и `/openapi.json` отключены в коде приложения по умолчанию (`ENABLE_DOCS=False`) и заблокированы на уровне Nginx Gateway с возвратом `404 Not Found`, предотвращая раскрытие структуры API внешним сканерам.
5. **Эшелонированная защита данных и RBAC (Defense in Depth)**:
   * **Защита от IDOR и BOLA**: Доступ к деталям, согласованию и файлам заявок строго ограничен автором, администратором, фактическим руководителем отдела (`head_id`) и менеджером проекта (`manager_id`). Посторонние менеджеры, руководители и сотрудники блокируются (`403 Forbidden`).
   * **Защита хранилища медиафайлов (Object-Level Authorization)**: Эндпоинт скачивания `/uploads/{file_path}` валидирует владение объектом в БД — конфиденциальные голосовые сообщения доступны только автору переработки, менеджеру проекта, начальнику отдела и администратору (`403 Forbidden` для посторонних пользователей).
   * **Предотвращение Mass Assignment**: Создание пользователей с повышенными ролями (`admin`, `head`, `manager`) возможно только через закрытый роут администратора.
   * **Контроль конфликта интересов**: Запрещено самосогласование собственных заявок руководителями отделов и менеджерами; действия администратора фиксируются в аудит-логе со специальным маркером.
   * **Машина состояний и защита от воскрешения заявок**: Запрет пересмотра заявок в финальных статусах (`APPROVED`, `REJECTED`, `CANCELLED`), запрет отмены отклоненных заявок (`400 Bad Request`), а также строгий запрет восстановления (`/restore -> 400 Bad Request`) заявок, по которым руководство уже вынесло решение (согласовано или отклонено).
   * **Целостность данных и отказоустойчивость структуры**: Валидация существования проектов (`404 Not Found`), проверка активности проекта как при создании, так и при частичном обновлении PATCH (`400 Bad Request` для неактивных проектов), валидация существования `head_id` при создании отделов (`404 Not Found`) и перехват `IntegrityError -> 409 Conflict`.
   * **Защита корпоративных лимитов проектов**: Менеджерам проектов запрещено изменять недельный лимит переработок `weekly_limit` (разрешено только роли `admin`).
   * **Санитизация формул Excel (CWE-1236)**: Экранирование лидирующих символов `=`, `+`, `-`, `@` для предотвращения атак Formula Injection при выгрузке отчетов.
   * **Корректность агрегации аналитики (CWE-840)**: Расчёт суммарных переработок (`total_hours`) в сводной аналитике учитывает исключительно фактически согласованные заявки (`APPROVED`), предотвращая искажение метрик трудозатрат и бюджетов отклонёнными или отменёнными заявками.
   * **Принцип запрета по умолчанию для медиафайлов (CWE-276 Default Deny)**: Эндпоинт `/uploads/{file_path:path}` при отсутствии привязки файла к согласованной заявке блокирует доступ (`403 Forbidden`) для всех непривилегированных пользователей, предотвращая несанкционированное чтение файлов из директории загрузок.
   * **Отказоустойчивость CRUD операций отделов и пользователей (CWE-755)**: Проверка существования руководителя `head_id` при обновлении отделов (`404 Not Found`), валидация существования `department_id` при регистрации и создании пользователей администратором (`404 Not Found`), а также обработка конфликтов внешних ключей с возвратом понятного кода ошибки (`409 Conflict`).
   * **Принудительный отзыв сессий при смене пароля (CWE-613 Concurrent Sessions Revocation)**: При смене пароля пользователем, подтверждении сброса пароля или сбросе пароля администратором вызывается полная инвалидация всех действующих Refresh-токенов пользователя в базе данных (`revoke_all_user_refresh_tokens`), прерывая скомпрометированные сессии на других устройствах.
   * **Устранение временного перекоса лимитов (Time Skew Mitigation)**: Расчёт суммарного недельного объёма переработок сотрудника при валидации лимитов выполняется строго относительно недели выполнения работ (`start_time`), а не текущего серверного времени (`now()`), устраняя обход лимитов при создании заявок задним числом.
   * **Защита административного контура от самоблокировки (CWE-284 Admin Self-Lockout & Demotion Prevention)**: Защита администраторов от случайной самодеактивации (`is_active: False`), самопонижения роли (`role != admin`), а также строгий запрет на деактивацию или понижение роли последнего активного администратора системы (`400 Bad Request`).
   * **Защита от переполнения, DoS и микросекундных манипуляций**: Строгие лимиты пагинации (`limit` <= 1000), валидация диапазонов дат аналитики (`start_date <= end_date`), строгая проверка минимальной длительности переработки (от 15 минут / 900 сек) в схемах создания и частичного обновления PATCH (`422 Unprocessable Entity`).
